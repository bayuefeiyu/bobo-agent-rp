# Import boundary

Copy this directory to `features/comfy-image-generation/` in a card, register `features/comfy-image-generation/module.json` in `manifest.feature_modules`, and copy `agents/image-prompt-writer/` into the card's `agents/`. Keep `workflows/agent-image-generation/` inside the module; `module.json.workflowFiles` registers it as `comfy-image-generation/agent-image-generation`. For Web/manual activation, copy or retain the runtime template's top-level `workflows/agent-image-generation/` wrapper, which calls the module workflow synchronously.

The copy is card-owned and never synchronizes with this global source. Importing the package does not configure a usable image workflow by itself. At the project root, use `adapt-comfyui-workflow` on the intended ComfyUI API-format workflow, resolve its prompt, seed, LoRA, output and connection bindings with the user, then save the confirmed profile and model-specific guide into the card-owned module copy. Do not copy profiles from another card blindly.

The target card must use the current Pi RP runtime and Web template, because the module's `image-generation` region, ComfyUI service, protected image proxy and background workflow execution are provided by the shared template. Importers must validate Agent/top-level-wrapper ID collisions and preserve the module workflow boundary; importing never activates an automatic trigger without the card/user's chosen runtime setting.

Generated files stay in the configured ComfyUI output directory. The module stores requests, prompt material, render state and output references, but does not copy or delete ComfyUI images when a chat or message is removed. Missing source files are reported as unavailable rather than rewriting a completed render as failed.

Image operations persist their request identity before prompt generation. A render in `submitting` or `submitted` is resumed by its stored ComfyUI task identity, connection URL and output-node mapping; it must not be submitted again merely because the original HTTP response or a later local state write was lost. The Web UI may therefore show an unresolved in-flight state until the original task can be queried. An explicit new generation uses a new operation identity.

Each request also owns one frozen effective snapshot per selected profile: the API workflow, bindings, fixed positive/negative prompt settings, model guide, output nodes, effective digests and connection address used for that operation. Renders reference those snapshots and store only their own prompt, seed, filename, payload digest and remote task identity. Credentials are never copied into a request. Replaying or recovering an operation reads its frozen request first and does not reload current profiles, preferences or chat selection; use **恢复原任务** to query the original `promptId`, and create a new operation when current profile settings should apply.
