# Feature-module Workflow v3 placement

## Candidate, review, and publication pattern

When several creative modules may write into the same fictional world concurrently, prefer a read-only candidate workflow, a top-level cross-module review, and a deterministic module-internal publisher. Candidates do not write authoritative data. Review stays inside the author-defined conflict scope; when changes are required it returns a complete publishable replacement rather than vague patch instructions. Each publisher holds its own collection lock and commits idempotently. The top-level workflow must call cross-module internal publishers because a module workflow may continue only into `module-external` workflows.

Use `documentSnapshotInput` when the called module needs the caller Agent's currently authorized documents; do not make the Agent recopy them. Bound retrieval with both `maxCalls` and a fixed or statically limited budget.

Read the data-design Skill's [workflow access](../../design-pi-rp-data/references/workflow-access.md) and [mutation/runtime](../../design-pi-rp-data/references/mutations-and-runtime.md) guidance before adding data nodes.

Modules expose complete workflows only, listed by `module.json.workflowFiles`; never expose a naked node or module-internal tool. Use `module-external` for query/transform work that does not modify authoritative state or cause irreversible external effects. Use `module-internal` for authority maintenance or external effects. By default, every internal workflow locks its whole owner module and preserves the legacy serial lane. A module that deliberately separates independently writable collections may declare exact top-level `writeLocks`; non-conflicting collection locks may then run concurrently, while a whole-module lock conflicts with every collection lock in that module. Internal workflows default to one instance. A keyed multi-instance internal workflow must declare a stable `dedupeKey`, a positive finite `maxConcurrentInstances`, and exact collection locks. Its key and invocation fingerprint come from normalized call `arguments`; identical concurrent calls share one child run, while the same key with different arguments is an operation conflict. The lock scheduler still serializes instances that touch the same collection. Every module workflow has no trigger and ends in exactly one `workflow-return`.

Top-level nodes call module workflows synchronously. A `call` node declares one fixed `target`. An `agent` or `code` node must list exact `module-id/workflow-id` references in `workflowCalls`; no wildcard grant exists. An Agent sees `rp_call` only when its node exposes at least one workflow and the target declares `agentCallable: true`. Code ignores `agentCallable` but still needs the exact node list. Module workflow nodes may call only `module-external` workflows; only top-level workflows may call `module-internal` workflows.

Use ordinary `agent` or `code` nodes for module work. Give each node only the collections, capabilities, views, and budget required for its task. Keep query-only narration separate from maintenance authority.

Randomness is a common runtime primitive, not module-owned authority. Grant an Agent the `rp_roll` tool in its Agent profile, or let a `code` node declare `runtimeServices: ["random"]` and call `await services.random.roll({key,dice,modifier,reason})`. Use a stable logical key so node retries replay the original roll. Do not implement a second random generator inside a module. A module may interpret the returned result according to its own rules and explicitly persist a derived fact when that fact belongs to its authority.

Resource workflows receive their normalized module catalog and module directory through the trusted code-node module input. Return a `document-set` when the number of independently readable files varies by call: it is a directory containing `DOCUMENTS.md`, rejects symbolic links, and crosses the call boundary as one declared export. Other explicitly declared directory inputs and exports use `kind: "directory"`; document inputs default to `kind: "file"` and may declare `"directory"` or `"either"`. A resource-only module has no `moduleAccess` because it owns no session collections.

If a module influences analysis, planning, writing, or checking, expose the required material through declared file or directory exports regardless of the module's internal storage. Record one or more non-exclusive integration modes in the design: `pre-creative` prepares material for the current task; `post-creative` processes completed prose for explicit delivery in a later turn; `memory-backed` archives information for later retrieval without necessarily exposing the generated material immediately. Define ordering, trigger, durable owner, and the later export/preparation workflow. Top-level wakeups do not carry workspaces across workflows or turns.

For node-to-node files, declare outputs and list only the intended subset in `workspaceHandoff.include`. The destination defaults to the declared output path under `handoff/<producer-node-id>/`, preserving a partial mirror; optional `as` is only for an intentional rename. Never hand off a whole node workspace, infer files by scanning, use a wildcard, or rely on an exclusion list. Missing entries, kind mismatches, unsafe paths, symbolic links, overlapping targets, and collisions fail the producing or receiving node. A caller that wants to pass a module return onward must redeclare and explicitly include that return; nested results never bubble automatically.

Declare every change document as a named output with format `unified-change-batch`. An Agent may call `rp_data_submit`; configure `dataCommit.onNodeEnd` for exact required outputs as the fallback. Never scan a workspace for drafts.

Order dependent changes. Parallel writers require an authored conflict strategy. Enable `best-effort` only when partial application is intentionally correct. Durable queryable results enter the owning module; intermediate files remain scoped workflow artifacts.

When a creator exposes an internal workflow to an Agent, warn the creator in development guidance that a successful child call may commit authority or trigger an external effect before the parent node or foreground turn later fails. Do not inject generic risk text, use-timing advice, or inferred calling policy into the RP Agent prompt; the node author's prompt alone decides when the Agent should call.
