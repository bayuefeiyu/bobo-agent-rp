# 独立卡包运行时实施方案

日期：2026-09-20。

状态：实施中。仓库根的独立卡打包器、卡内运行模板、轻量选卡器及基础验证已落地；正式安装和旧卡迁移尚未执行。本文保留实施顺序与验收条件，不把临时卡测试当作创作者手动测试。

方案修订：采用不依赖 Pi 的选卡启动器。全局设置由根目录 Skill 启动根目录配置前端管理，单卡设置和聊天记录由卡内前端管理。

## 1. 目标与保证

一张卡完成转换并经过创作者测试后，其运行所需的项目代码、提示词、Agent 定义、工作流、模块和行为配置随卡固定。升级仓库模板、转换另一张卡、修改全局创作默认值，均不得改变这张卡的运行依赖或默认行为。

保证适用条件：卡包自身未被主动修改，基础引擎处于已验证兼容范围，所选外部服务仍提供所需能力。这里保证的是程序、规则、数据协议和配置来源的稳定，不承诺模型逐字生成相同文本。

“固定”指不再跟随上游自动变化。创作者仍可在根目录维护指定卡；用户仍可通过卡内配置界面主动调整自己的设置。卡修改后，原有测试记录不能冒充对新版本的验证。

基础引擎包括 Pi、Node 和 Pi 提供的 SDK/模型适配能力。项目自己的工作流引擎、数据存储、Agent 执行、Team、上下文装配及 Web Bridge 属于卡内运行时，不能因为名称里有“引擎”而留在共享层。

补充核实：

- 当前 `assets/pi-rp-runtime` 共 124 个文件，约 1.24 MB，包含测试；Web 模板约 0.32 MB。这支持采用文件副本，不值得为这些内容承担实时共享的兼容成本。
- 原先 `assets/card-runtime/prompts` 与 `assets/pi-rp-runtime/prompts` 有两套维护副本；实施时已移除前者，打包器只从后者复制。
- `play/` 仍被 Git 忽略。项目源、规范、打包器及测试应提交 Git；安装副本、个人设置和存档继续作为本地数据。
- 现有规则已禁止后续转卡自动覆盖已安装运行时。本次方案解决仍然存在的结构性耦合，不把尚未核实的“每次转卡必然覆盖共享文件”当成既成事实。

## 3. Pi 加载边界与启动方式

本机安装的 `@earendil-works/pi-coding-agent` 为 0.86.0。本次只读检查了该版本的 `docs/usage.md`、`docs/extensions.md`、`docs/sdk.md`，以及 `dist/core/resource-loader.js`、`dist/core/extensions/loader.js`。

已确认：

- Pi 支持 `-e <扩展路径>`，并支持 `--no-extensions -e <指定扩展>`。
- 可关闭 Skill、prompt template 和 AGENTS/CLAUDE 上下文的自动发现，再显式提供游玩资源。
- Pi 的扩展加载器使用 jiti，并提供 Pi SDK、TypeBox 等导入别名。不能将“Node 直接 import 扩展成功”当成唯一集成验收路径。
- SDK 允许显式设置 ResourceLoader 和扩展来源；目前项目已经用它隔离 Worker。

推荐采用**独立选卡页面＋卡绑定的 Pi 进程**：

1. 用户通过普通脚本启动轻量本地服务及选卡页面。此时不启动 Pi，不调用模型，也不加载卡内执行代码。
2. 服务扫描 `play/cards`，读取用于展示的卡 ID、名称、简介和封面引用；只读卡元数据，不解释 workflow、module 或存档内容。
3. 用户选卡后，启动器检查该卡的启动描述和兼容声明，再启动独立 Pi 进程，显式加载这张卡的扩展及游玩 Skill，关闭隐式资源发现。卡内 Web 服务就绪后打开对应前端。
4. 第一版可保持 Pi 的工作目录为 `play/`，降低路径迁移风险，但代码必须使用显式路径上下文区分 cardRoot、playRoot、sessionRoot 和卡内用户设置目录。
5. 卡运行时只允许打开自己绑定的卡，不能通过更换 cardDirectory 来执行其他卡。
6. 卡内前端提供“返回选卡”入口，卡目录与跨卡历史列表统一由启动器展示。选择另一张卡时，启动器先检查目标兼容性，等待当前前后台任务结束或完成用户选择的取消，再关闭旧实例、启动目标卡实例。单纯返回选卡页面不等于取消正在运行的任务。
7. 切换失败时保留旧卡和存档，提供重新打开入口；旧页面不能继续把写请求送给新卡。
8. 同一卡的聊天列表、新建聊天、恢复及删除聊天全部由该卡前端和运行时处理；启动器不读取聊天内容、不选择具体存档。跨卡切换不沿用上一张卡的 Pi 对话上下文、模块缓存或工具注册。

启动器接口第一版限定为：卡目录、最近游玩记录、启动、就绪地址、停止、切卡及错误状态。前端只显示选择与启动所必需的信息，不加入模型、Agent、工作流、玩家或全局设置面板。凭证不经过启动器或命令行。卡内仍保留可直接启动的入口，启动器不是唯一恢复通道。

### 3.1 选卡页面与最近记录

页面保留两个主要区域：

- **所有卡**：展示本地卡的名称、封面及简短介绍；按名称、ID 和简介搜索。搜索只处理元数据，不启动 Pi、不读取正文或存档。单张卡的元数据损坏不妨碍其他卡显示。
- **最近游玩**：按最近一次成功打开卡前端的时间倒序排列，每张卡只保留一条，重新打开时移到首位。点击仍是打开该卡，由卡前端决定新建或恢复哪段聊天。

第一版将“成功启动并收到卡前端就绪信号”定义为最近游玩记录的更新时间；点击失败不更新，打开选卡页面或搜索也不更新。时间由启动器记录。启动器不通过扫描聊天文件推断活跃时间。

启动器持久化数据仅需版本化的最近记录文件，例如 `launcher/state/recent-cards.json`，条目包含卡 ID 和最近成功打开时间。卡名和封面优先从当前目录读取，不保存副本；卡删除后历史条目不提供启动，卡恢复后可重新关联。重复卡 ID 明确报冲突，不任意选择。历史损坏不能阻止卡目录显示或卡启动。

第一次使用没有历史时显示空状态。选卡页没有必要记住模型、玩家名、聊天 ID 或工作流参数。避免双击造成同卡重复进程；关闭浏览器页面不自动强杀后台任务。第一版默认只管理一个活动卡实例。

### 3.2 三个前端的职责

| 前端 | 启动方式 | 职责 |
| --- | --- | --- |
| 根目录配置前端 | 根目录 Skill | 全局创作参数、模板默认值及供新卡采用的配置 |
| 选卡启动器 | 普通代码脚本，无需 Pi | 卡目录、搜索、最近游玩、启动状态 |
| 卡内前端 | 选卡后由该卡运行时启动 | 游玩、该卡设置、聊天记录切换和模块界面 |

三者不要求复用完整应用壳。启动器用独立的最小 HTML/CSS/JS 和 Node 本地服务即可，避免引入完整配置前端和业务依赖。全局配置改动仍只影响以后生成或明确导入配置的卡。

这是推荐设计，不是已完成的集成验证。实施第一阶段必须用真实 Pi 加载两个最小卡运行时，验证 SDK 导入、资源隔离、前台上下文和进程生命周期，再推进大范围搬移。不得凭文档就认定动态加载和切卡已经通过。

## 4. 目标文件归属

建议卡包结构：

```text
play/
  launcher/                         # 独立选卡页面、本地服务及进程启动
    state/recent-cards.json          # 最近成功打开的卡，不记录聊天
  cards/<card-id>/
    manifest.json                   # 卡定义，引用启动描述
    runtime-lock.json               # 来源、运行时/协议版本、文件清单
    runtime/
      engine/
        extensions/pi-rp-web.ts
        lib/*.mjs
      skills/                      # 与本卡运行时配套的游玩 Skill
      workflow/                    # 现有卡内 workflow 支持脚本
      launch.json                  # 入口、启动协议和兼容声明
    prompts/
    agents/
    workflows/
    features/
    web/                           # 前端与后端一起随卡固定
    defaults/                      # 完整行为默认值，无个人密钥
    config-profiles/               # 本卡配置覆盖
    settings.json                  # 本卡用户选择和显示设置
    core/、context/、openings/等
  sessions/<card-id>/<session-id>/ # 保持现有存档布局
```

`runtime/engine` 用于避免与已有 `runtime/workflow` 冲突。具体 schema 字段在第一阶段定稿；不为了路径重组改写业务语义。

| 内容 | 目标归属和读取规则 |
| --- | --- |
| 项目运行库、Pi RP 扩展、工具定义、权限检查 | 卡内；导入只指向本卡文件或已声明的引擎依赖 |
| prompts、角色标记装配、模型前后缀 | 卡内；缺少声明文件报错；明确可选项可为空 |
| Agent、Team、workflow、模块及其代码/数据定义 | 卡内；复制完整选定依赖，禁止依赖全局兜底 |
| 工作流并发、失败策略、节点绑定 | 卡内完整默认值＋本卡配置档案覆盖 |
| 模型名称、协议参数、采样/思考参数、模型提示词 | 卡内配置；个人模型目录只提供显式导入来源 |
| API key、认证资料 | 继续放操作系统缓存，保留项目/卡隔离；通过引用取得，不打包进卡 |
| 玩家档案库、头像库 | 卡内用户设置；可显式导入个人资料，开局形成会话快照，不随全局修改改变已开局角色 |
| 字号等纯显示偏好 | 卡内用户设置；初始默认值随卡复制，不进入剧情上下文 |
| ComfyUI 连接地址、本机输出目录 | 卡内连接设置，可显式导入；token 继续使用外部凭证缓存 |
| ComfyUI workflow、profile、种子规则和生成参数覆盖 | 卡内；不得再继承共享 profile overrides |
| 会话数据、运行记录、工作区 | 保留 play/sessions 布局；由对应卡运行时解析与写入 |

`pi:current` 是现有的主动模型选择机制，可以保留。启动时显示/记录实际解析的 provider、model 和关键参数；不得声称此选择固定了模型。创作者可选择并保存明确模型配置，发布测试记录写明测试使用的模型。

全局创作配置由根目录配置前端管理，作用是“新卡打包时的输入”或“显式导入配置”，不能成为旧卡运行时的动态默认源。新架构不要求 `play/settings` 承担公共参数中心；现有文件仅在 legacy 卡仍依赖它们时保留，迁移时按明确范围复制到卡内。密钥仍留操作系统缓存，不因参数卡内化而写入卡包或启动器历史。

## 5. 源码、打包与发布记录

### 5.1 单一创作源

- 暂保留 `assets/pi-rp-runtime` 作为运行库、Agent、工作流、默认配置及提示词的唯一开发来源。
- `assets/card-runtime` 保留卡特有支持脚本，删除重复 prompts 的维护责任，由打包器从唯一来源生成卡内 prompts。
- `assets/pi-rp-web` 继续作为 Web 创作源；打包时与该次运行时版本一起复制。
- 新增 `assets/pi-rp-launcher` 存放轻量启动器源。
- 根目录配置预览继续使用这些创作源，通过明确的 development 模式读取；play 模式严格卡内解析，不能共用含糊的 card-or-global 回退函数。

### 5.2 确定性打包

新增独立打包脚本，例如 `scripts/package_card_runtime.mjs`：

1. 解析明确的源根、目标卡和选定模块/工作流/配置。
2. 检查冲突，默认拒绝覆盖已经存在的卡运行时；重转或升级使用专门的明确模式。
3. 将项目运行库整体复制，排除测试、开发文档、缓存和密钥；不先做脆弱的按函数裁剪。
4. 复制选定定义及其完整依赖，展开基础默认配置和模型提示词文件引用。
5. 对 Agent/Team、workflowCalls、模块调用、脚本导入、promptFile 等进行依赖闭包检查。动态文件引用使用显式声明并在真实运行测试中补充验证。
6. 在暂存目录完成文件清单、校验和及结构验证，成功后发布目标；失败不留下半成品正式卡。
7. 打包只写该目标卡。安装/更新启动器是独立操作，普通转卡不能附带覆盖它。

这次应把“操作人员遵守复制规则”升级为脚本可以验证的边界。禁止跨卡软链接、junction 或链接回仓库模板；禁止用绝对开发路径作为包内依赖。

### 5.3 版本与测试记录

`runtime-lock.json` 至少记录：运行时版本、打包格式、启动协议版本、存档/数据协议版本、源 revision、源是否有未提交修改、实际文件校验和、模块来源、已测试 Pi/Node 版本、外部依赖要求。只有经过测试才能扩大兼容版本声明，不用“同一大版本”代替证据。

校验和用于诊断、发布比对和识别创作者改动，不把“与模板不同”直接判为非法。缺失运行必需文件、入口错误或协议不兼容须拒绝启动；合法手动修改提示词后应标记原测试记录过期，并允许按创作者流程重测。

自动检查完成后，创作者在真实游玩中测试开局、多轮、后台流程、保存恢复及所选模块。记录实际测试版本、配置和结果，再形成发布基线。自动工具不得代替创作者宣称“手动测试通过”。

## 6. 按阶段实施

### 阶段一：启动协议与真实 Pi 验证

产物：无需 Pi 的双区域选卡页面及本地服务、最近记录存储、最小卡绑定入口、路径上下文、启动描述 schema、兼容检查、隔离测试夹具。

- 先验证没有 Pi 进程时仍可浏览、搜索和读取最近记录；只有选择并启动卡时才调用 Pi。
- 用两份具有可区分行为的最小运行时验证显式扩展加载；从实际 Pi 扩展环境验证 SDK 与 TypeBox 导入。
- 检查主会话、Worker、Team 的资源来源及环境设置来源，禁用无关自动发现，并显式注入必要设置。
- 验证停止、切卡、失败清理、端口释放和上下文不串卡。前后台未结束时不得直接杀进程丢弃写入。
- 对需要支持的 Pi/Node 组合建立最初的兼容记录。

此阶段通过后才固定入口布局和启动器交接方式。如果遇到 Pi 实际限制，应调整并报告启动设计，不缩减独立性保证。

### 阶段二：卡内运行时及配置解析

主要改动：`pi-rp-web.ts`、`rp-config-store.mjs`、`rp-author-prompts.mjs`、`rp-config-profiles.mjs`、`rp-comfyui.mjs`、模型/用户设置和 Web 切卡接口。

- 将扩展与全部项目库打包到卡内，所有 paths 从显式上下文取得。
- 拆分游玩和开发预览的配置来源；独立卡模式禁止共享 Agent/workflow/prompt/default 回退。
- 去掉游玩启动时对共享行为配置的 ensure/规范化写回。
- 将卡内玩家、显示和服务连接配置与 `play/settings` 解耦；卡前端保留完整聊天管理，跨卡目录改为返回选卡启动器。
- 配置编辑、恢复默认、重试和导入全部使用同一张卡的基线；“恢复默认”必须恢复卡发布时的默认值。
- 把旧 `runtime/agent/...` 等覆盖键转换成稳定卡内键，迁移时保留实际有效值。
- 普通游玩配置不修改发布默认定义，写入本卡用户覆盖；任何数据迁移另行执行。
- 继续遵守玩家名约定：制卡保留 `{{user}}`，开局绑定真实姓名，正式产物直接使用姓名；不开启自动改名兼容。

### 阶段三：打包器、校验器与创作工具

主要改动：新增打包器与启动器模板；更新转卡 Skill、目标卡结构、Web/工作流/验证文档、根目录配置 UI、release manifest 检查。

- 转卡从唯一创作源生成完整独立包，不优先读取旧的 `play/workflows` 安装副本。
- 验证每个模型/Agent/Team/模块/工作流引用闭包、启动入口、路径约束和 runtime-lock。
- 当前根校验器识别 legacy 与独立包格式，不能用最新版业务规范强迫所有旧包升级。旧运行协议的校验依靠版本分派或随包提供的兼容检查器。
- 将发布相关规范、打包源和稳定性回归测试纳入 Git。安装副本继续忽略；卡是否另行发布由卡作者决定。

### 阶段四：旧卡迁移能力

主要改动：audit/upgrade 的 inventory、依赖升级规则和指定卡迁移工具。

- 无 runtime-lock 的卡标识为 legacy，不自动拿最新版模板填齐。
- 迁移时先清点这张卡**实际使用的已安装运行时、共享基线和覆盖值**；冻结这一套来源，再做启动和路径适配。不能把“依赖独立化”混成“升级所有模块到最新”。
- 根模板与已安装运行时代码可能不同，必须分别记录；无法恢复实际依赖时报告缺项。
- 在隔离副本验证后才处理明确指定的正式卡；保留卡包备份。涉及存档变化必须另列目标、备份、迁移和回退步骤。
- 新启动器可以显示 legacy 状态并引导使用原有启动方式；不能用新运行时自动接管 legacy 卡。旧共享目录暂时保留，待使用者主动迁移全部依赖它的卡后再单独清理。
- Seraphina 仅作为隔离测试样本。实施默认不修改正式 `play/cards/seraphina`、已安装共享 runtime 或存档。

### 阶段五：稳定性回归与文档交付

核心验收是“上游变化后 A 卡仍使用 A 的依赖”，需要在测试中观测实际读取与执行来源，不能只比对文件时间戳。

| 场景 | 必须验证 |
| --- | --- |
| 打开启动器、搜索或浏览最近记录 | 无 Pi 进程启动、无模型调用、无卡代码执行，也不读取聊天内容 |
| 首次打开、重复打开、启动失败、卡删除、历史损坏 | 最近记录去重、按成功就绪时间倒序；失败不更新；异常历史不妨碍启动其他卡 |
| 卡内前端切换聊天或恢复旧聊天 | 仅由该卡处理；启动器不持有聊天 ID 或解析存档 |
| 打包 A 后，大幅修改根模板并打包 B | A 文件校验和不变；A 的提示词、Agent、默认策略、代码入口和关键行为仍来自 A；B 使用新版本 |
| 测试环境移除共享 prompts/agents/workflows/.pi/lib | A 可以开局、完成确定性流程、保存并恢复 |
| A 缺失一个声明依赖，顶层恰好存在同名文件 | 明确报缺失路径，不使用顶层文件，不自动修补 |
| A 与 B 使用不同运行时代码和配置格式 | 分别启动及切换成功，不混用工具、库缓存、上下文和 Web 后端 |
| 修改全局模型提示词、workflow policy 或出图 overrides | A 的行为配置不变；显式导入/修改 A 时才变化 |
| 创作者改动 A 的提示词后执行发布检查 | 能识别修改和测试记录失效；不覆盖手改内容 |
| 引擎版本不兼容、启动失败、切卡中断 | 启动前给出明确错误或可恢复状态；不写坏 A 的存档 |
| 同卡保存/恢复、事务恢复、后台任务、Team、前台主叙事 | 完成项目级集成回归；模拟模型用于确定性断言，真实模型另做冒烟 |
| 根目录开发预览 | 仍能管理创作源配置，不创建游玩卡/会话，不传播到旧卡 |
| 打包失败或目标冲突 | 仅暂存目录有变化，原卡、启动器、个人设置和其他卡无变化 |

最终人工验收：创作者测试卡 A，更新模板并生成卡 B，再打开 A 的既有存档继续游玩。记录完整环境与结果。对模型输出比较结构和流程，不做逐字一致断言。

## 7. 实施范围与完成标准

本方案后续“开始实施”的默认范围：仓库根的运行模板、启动器源、打包/验证脚本、相关技能文档、维护工具、根配置预览和测试；允许建立隔离测试卡与模拟存档。

安装到正式 `play/`、迁移正式卡、修改真实存档、删除旧共享文件、提交或推送 Git，分别按用户明确指定的目标执行。本轮只新增本方案文档。

完成标准：

1. 新转换卡不依赖项目级共享业务代码或行为默认值。
2. 必要依赖缺失时明确失败，不从顶层或另一张卡回退。
3. 新卡转换和根模板更新无法修改旧卡或其依赖。
4. 启动器和引擎的兼容边界有声明、实际验证及失败处理。
5. 自动稳定性回归、真实 Pi 集成检查和创作者测试记录各自有证据，不能互相替代。

实施记录（2026-09-20）：在系统临时目录复制 Seraphina，并将 `{{char}}` 解析为确定名字后，打包成两张独立测试卡。选卡器在没有 `play/settings` 的目录下启动 Pi 0.86.0，两个卡的 Web API 分别就绪；A 卡读取卡内 19 个 Agent 和 2 个工作流，切到 B 卡后最近记录顺序正确。关闭卡的 RPC 指令若已确认却未使进程退出，启动器在确认无前后台任务后关闭其输入，最后清理进程；拒绝关闭或无法确认空闲时保留旧实例。卡包记录 Node 主版本和已测试 Pi 版本，启动前检查。运行库 299 项、Web 7 项、打包/选卡 4 项及卡包资产校验通过。没有调用真实模型、执行多轮游戏流程或迁移真实存档；这些仍是下一阶段验收项。
