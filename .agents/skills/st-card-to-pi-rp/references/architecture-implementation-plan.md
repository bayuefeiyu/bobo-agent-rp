# 项目结构与工程架构优化实施方案

日期：2026-10-09<br>
状态：方案已编写，尚未实施<br>
适用范围：仓库开发源码、运行时与 Web 模板、全局模块、工程验证和当前文档<br>
依据：本次 Architecture & Project Structure Review 中 R1—R7，以及用户对报告第一至第四部分优化建议、第五部分保留项的确认。

## 1. 目标与实施前提

本次优化以降低修改成本、明确职责和提高验证可复现性为目标，不增加业务功能，不调整角色设定、创作提示词内容或业务规则。

用户已明确：项目未曾发布，不必考虑旧内容兼容。因此，本方案替代审查报告中为兼容旧接口而建议保留适配层的部分：

- 只维护一套当前支持的协议、配置方式和工程入口。
- 可以删除被新实现替代的旧页面、旧专用接口、旧格式读取和仅为旧布局服务的回退分支。
- 内部接口和尚未发布的外部接口可以调整，当前调用方、模板、脚本、测试及文档必须在同一阶段更新。
- 不编写旧卡、旧会话或旧配置迁移脚本，不保留双写、双读、旧接口别名或长期弃用期。
- 协议版本不因文件拆分机械升级；只有数据形状或契约含义确实变化时，统一调整当前版本和全部源码资产，拒绝旧版本而不是自动转换。
- 无需旧版本兼容，不等于可以改变当前功能语义。事务原子性、幂等、权限、来源追踪、取消和恢复、配置生效时机均继续受到回归测试保护。
- 当前格式下的正常恢复、缺省值、可选能力和错误处理不是“旧兼容”，不得因清理历史分支而删除。

授权边界：本轮请求为编写完整实施方案，不包含立即实施代码优化。后续实施按本方案阶段推进；不因文档已存在而自行开始。

## 2. 源码基线与范围

### 2.1 审查基线

审查针对 2026-10-09 当前工作区实际文件，包含未提交修改和未跟踪源码，而非只针对 HEAD。开始实施时必须重新记录工作区状态，不得把既有改动当作本方案产物，也不得回退或覆盖用户工作。

审查清点得到：

- 567 个未被 Git 忽略的现存文件。
- 65 个 JavaScript 测试文件、6 个 Python 测试文件；这些是文件数，不是测试通过数。
- 公共运行库中 56 个非测试 MJS 文件。

- 只读注册和归一化检查通过：上述组件、6 个数据契约、5 个资源目录及6个前端视图。

这些结果用于定位改造范围，不是完整测试验收。本轮审查没有执行会创建夹具或产物的完整测试，也没有执行真实模型或 ComfyUI。

- 真实模型或外部服务调用不进入默认验证；若另行执行，应单独记录输入、环境、范围和结果。

不支持旧内容时，处理方式是由使用者后续显式重新生成或安装当前产物，不在本方案中自动重建、迁移、删除旧内容。

## 3. 保留的架构决策

以下内容已经确认合理，各阶段不得借整理之名更改：

1. 保留 Skill 源、模板、全局模块、独立卡包和会话数据的分层。
2. 保留独立卡包的复制交付与依赖冻结，不改成对根源码的实时依赖。
3. 保留模块内部聚合 Agent、工作流、提示词、资源和数据契约的组织方式。
4. 保留模块限定引用、manifest 注册与明确所有权。
5. 保留单一维护源和受校验的生成副本，不把副本改成运行期跨模块路径引用。
6. 保留统一数据层的存储、查询、事务、视图分工，不引入数据库或 ORM 替换现有机制。
7. 保留工作流引擎与实际节点执行器的分离。
8. 保留原生 Web、ES modules 和较少生产依赖，不引入前端框架或必需的打包器。
9. 保留作者默认、开发配置方案、卡级设置和聊天状态的不同作用域，不合并所有者不同的数据。
10. 不执行全仓命名统一，不为目录外观搬迁全部运行库，不建立宽泛的 utils 杂物目录。

## 7. S2：统一验证与开发依赖

### 目标结构

新增根目录开发入口 `package.json`、对应锁文件、`scripts/verify.mjs` 和 `scripts/verification-suites.mjs`。现有业务源码和模板不搬迁。新文件需纳入 `.gitignore` 的精确放行及发布完整性检查。

根包仅用于开发验证，不改变卡包运行时交付，不把根 node_modules 复制进卡。

### 工作项

1. 提供统一命令：
   - `npm run verify`：默认基础验证，不调用外部模型或服务。
   - `npm run verify:integration`：运行指定 Pi 宿主的离线集成验证，环境缺失即失败。
   - `npm run verify:all`：基础验证与必需的离线集成验收汇总。
   - `npm run typecheck`：不输出编译产物的接口类型检查。
2. 默认套件自动发现 `ENGINE/lib`、`MODULES`、Web 和各 Skill scripts 中实际属于发布源码的测试；保留必要排除清单并解释原因，不使用逐个模块名称的易漏清单。
3. Python 测试使用明确的可用解释器，支持环境变量指定路径并进行预检。未发现 Python 时报告环境缺失，不能静默忽略整类测试。
4. 收集每个套件的执行、失败、跳过、耗时和退出码；启动失败、超时、非零退出码以及未完成的必需套件使验证整体失败。
5. 不以某个固定测试数量作为长期验收门槛；展示发现与执行数量，并检查必需套件没有被意外遗漏。
6. 锁定实际导入的开发依赖。Pi 和 TypeBox 通过统一位置加载，停止各测试自行猜测 APPDATA 的不同路径。
7. 用一个权威开发运行时声明记录已验证 Pi 版本和 Node 基线，打包器读取该声明生成 launch/lock 元数据，替代散落的版本字面量。已打包卡仍使用自己的冻结声明。
8. 若离线测试需要访问 Pi 的内部文件，集中到测试适配器，并在预检中校验预期文件和版本；不把该适配器扩展成生产 SDK 包装框架。
9. 新增开发类型检查，先覆盖 Pi 宿主边界、新提取接口和相关 JS/JSDoc。类型覆盖范围必须明确，不用整文件 ts-nocheck 或大量 any 把错误隐藏为通过，也不要求本阶段将全部 JS 转为 TS。
10. 将格式/静态检查保持为无自动修复模式。优先语法、类型、未解析引用及实际高价值规则，不引入全仓格式重写。
11. 生成一致性只运行显式 `--check`；`verify` 不得执行同步、安装、转卡或修复操作。测试可以在隔离夹具目录创建与清理文件，但不能改写源码。
12. CI 复用同一入口。先建立 Windows 主验证环境，符合实际开发与启动器场景；无平台依赖的基础测试可再加入 Linux，不把跨平台部署扩张为本次目标。
13. CI 不配置模型或 ComfyUI 凭据，不把真实外部调用作为合并前必需检查。

### 验收

- 干净检出后按文档安装开发依赖，即可执行默认验证。
- 近场叙事、生图执行、模块注册、提示词控件和打包测试都被发现。
- 可人为制造一个测试失败、一个缺失宿主和一个依赖版本不符，分别得到正确的非零退出码及清晰诊断。
- 集成模式不会在 Pi 缺失时报告整体通过；快速模式的跳过逐项可见。
- 默认验证不会触及 `play/`、全局 Pi 用户状态、个人设置或网络服务。
- 根依赖和测试夹具不进入新卡包。

### 成本与风险

中等成本，产品行为风险低。Node/Pi 版本声明与实际测试环境必须对应；不能仅因打包命令运行在某个 Node 版本上，就宣称该组合已经验收。

## 8. S3：建立跨语言协议一致性基线

### 修改范围

新增 `CONVERT/tests/contracts/`，包含数据样例、预期结果和规则责任说明；为 Python 与 JavaScript 分别增加消费这些样例的测试入口。

### 工作项

1. 建立规则责任表：
   - 结构契约：版本、字段、类型、枚举、组件归属、路径形式。
   - 运行时语义：默认值归一化、调用权限、DAG、节点约束。
   - 卡包关系：文件存在、组件注册、跨模块引用、数据访问声明。
   - 转换要求：来源映射、资料完整性、设计不变量。
   - 启动完整性：launch/lock、依赖版本、路径、文件清单和哈希。
2. 对重复实现的规则提供共享样例，优先覆盖 Module v7 字段、Workflow v4、限定引用、owner、节点类型、路径、Agent/工作流注册和调用目标。
3. 每个样例包括规则 ID、输入、适用校验层、预期接受或拒绝及必要诊断类别。某层无需执行的规则显式标注，不要求所有校验器输出完全相同的错误文本。
4. 正反例来自实际契约和当前资产，包含缺字段、额外字段、错误版本、所有权冲突、未注册组件、路径越界及非法节点组合。
5. 将真实模块装配测试和协议样例互补：前者防止规范与发布资产脱节，后者验证明确拒绝条件。
6. 当前支持版本以外的样例明确拒绝。旧版本可以作为拒绝输入存在，不实现旧版本解析器。
7. 暂不引入 Schema 到多语言代码的生成体系。只有稳定的字段集和枚举确实重复时，才使用简单共享声明。

### 验收

- JS 与 Python 在声明为共同规则的样例上结果一致。
- 规则差异能由责任表解释，不能靠跳过失败样例解决。
- 同一协议修改只需补充一份输入样例，即可同时验证两种实现。
- 样例全部使用合成或公开模板数据，不含角色原卡、会话或凭据。

### 成本与风险

中等成本、低风险。本阶段先暴露差异；若发现真实规则冲突，应根据当前权威协议作出并记录决策，不把某个实现的偶然行为直接当作规范。

## 9. S4：收敛配置目录装配

### 修改范围

`CONFIG_SKILL/scripts/start-config-ui.mjs`、`ENGINE/extensions/pi-rp-web.ts`、配置 store/profile 相关测试，并新增 `ENGINE/lib/rp-config-catalog.mjs`。

### 工作项

1. 提取工作流字段声明，替代 `workflowFields` 与 `workflowConfigFields` 的重复实现。
2. 提取模块、Agent、工作流的目录项生成和限定配置 key 生成。
3. 模块设置默认值按 frontend-view 中 `settings-form` 的 collectionId、recordId/recordType 和 data contract 的 storage 读取，不假定集合必定名为 settings，也不默认取数组第一条。
4. 支持现有协议允许的 initialSnapshotFile 和 initialRecordsFile，记录选择必须明确；选择不到或存在歧义时按契约报告错误，不静默选择另一条。
5. 同一模块存在多个设置 region 时，先明确每项的集合/记录身份，防止平铺字段互相覆盖。只支持协议明确的映射，不借此增加通用表单平台；若当前 profile 表示无法无歧义承载，直接统一调整当前表示和消费者，不增加旧格式回退。
6. 作者默认值与配置覆盖值分别返回和应用，避免将有效值重新当成默认值。
7. 开发模式和卡模式只负责提供模块来源、文件读取、作用域与权限。两种模式调用相同目录构造函数，存储仍然分离。
8. 清理相关旧格式迁移和重复合并函数前，逐项确认它们确实仅服务旧格式，而不是当前覆盖语义。

### 验收

- 对相同作者模块，两种模式的目录基础值和字段含义相同，差异仅为明确的作用域元数据。
- 测试覆盖非 settings 集合、两种初始化来源、精确记录选择、多 region、缺失记录和同名字段冲突。
- 覆盖优先级、只读内置方案、配置导入导出和凭据隔离行为不变。
- 两个宿主不再各自实现一套 workflow 字段和模块默认值推导。

### 成本与风险

低至中等成本和风险。主要风险是把现有覆盖值与作者默认混用；测试必须明确区分二者。

## 10. S5：拆分 Pi 扩展宿主

### 拆分原则

`ENGINE/extensions/pi-rp-web.ts` 最终只承担 Pi 事件/命令/工具入口注册及依赖组装。按职责拆分，不以任意行数限制作为完成标准，不把巨型闭包原样搬到另一个文件。

### 建议内部模块

| 模块 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| rp-host-session.mjs | 当前卡/聊天生命周期、选择、结束、状态快照与回合协调 | 各节点具体执行和表单字段规则 |
| rp-node-executor.mjs | 根据节点类型调度现有执行能力、组织本次执行输入输出 | Web 路由、页面或全局配置写入 |
| rp-node-data-access.mjs | 构造受授权与冻结读取限制的数据服务 | 扩大调用者权限、直接绕过事务 |
| rp-web-bridge.mjs | 将 Web 操作绑定到宿主服务 | 重复实现引擎、协议和模块领域规则 |
| rp-config-catalog.mjs | S4 建立的配置目录构造 | 保存会话和启动模型 |

若单个执行路径仍过大，可进一步按 agent/team/code 拆分，但必须存在独立依赖和行为测试。不要预先为每个小函数创建文件。

### 实施步骤

1. 列出当前 active、rpRun 和执行任务的所有读写点，明确状态所有者及生命周期。
2. 先提取已具备清晰参数的纯函数和服务工厂，接回原入口并运行定向测试。
3. 为宿主、节点执行上下文和 bridge 建立最小接口；通过显式参数传入能力，不传入一个可任意修改所有状态的大对象。
4. 提取数据访问装配，保留 run、node、read-view、capability 和 source revision 的关联。
5. 提取节点执行逻辑，继续由 RpWorkflowEngine 注入 executor 调用，不更改调度器的并发和锁语义。
6. 提取会话生命周期和 Web 操作，避免请求期间在 await 后错误使用已经切换的 active；每次操作应绑定明确宿主或会话身份。
7. 将能直接测试的行为从源码字符串断言改为实际服务调用。对必须约束的静态工具声明继续保留专门检查。
8. 删除不再使用的顶层 helper、旧分支和重复类型；更新打包清单及加载测试。

### 必需行为验收

- 开场、正常回合、正文发表与回合终结保持当前语义。
- agent/team/code/call 通过同一受控交付、授权及数据边界。
- 节点失败、取消、重试、换模型和当前格式的重启恢复不会重复提交或永久阻塞。
- 等待子工作流释放执行槽，锁按既有规则保留或释放。
- 冻结数据读取与来源修订检查不能退化为读取最新值。
- 授权资料交接和工作区白名单不扩大；未授权工具和跨模块写入仍被拒绝。
- 会话结束或切换不能把旧执行结果写入新会话。
- 对 SDK 使用离线确定性替身或固定流，不依赖真实模型验证宿主控制流。

### 成本与风险

高成本、中高风险。按“数据服务 → 执行器 → 会话 → bridge”的小批次实施，每批完成后接回入口并验证。一个批次出现新增失败时先恢复该批次的一致状态，不继续搬迁其他职责掩盖问题。

## 12. S7：明确生图模块适配边界

## 16. 风险控制与交付方式

每阶段形成一个可审查的完整变更批次，包含代码、当前消费者、模板、定向测试和必要文档。阶段之间不得长期保留两套实现；确需中间接线时在本阶段结束前完成替换并删除临时代码。

回退是开发过程的代码批次回退，不是旧格式兼容。只回退本次明确拥有的修改，不能使用覆盖整个脏工作区的重置方式。实现前已有改动必须保留；必要时在独立开发分支或隔离检出中建立可复现基线。

阶段结果统一记录：完成项、删除项、接口调整、执行检查、失败/跳过、剩余风险和下一阶段依赖。只有验收条件实际满足才将阶段状态改为完成。
